# Runbook: headless Mac mini — авто-восстановление после блэкаута (история с шифр-сейфом)

**Для кого:** оператор (и любой, кто унаследует этот сервер). **Когда:** понять, почему на хосте так настроено, воспроизвести или откатить.
**Дата:** 2026-07-13. **Хост:** Mac mini 2018 (Macmini8,1, Intel + чип T2), macOS 15.7.7 Sequoia, headless, доступ по Tailscale + SSH.

---

## ⚠️ ИТОГ (читать первым)

**Финальное состояние: FileVault СНЯТ (мини сам поднимается после блэкаута + Tailscale ✓), а шифр-сейф — ПРОБОВАЛИ И РАЗОБРАЛИ. Мини сейчас = незашифрованный сервер; при краже читается всё.**

Почему сейф отменён: истинная цель была защитить **живые данные iCloud Drive (Obsidian, 29 GB)**. Оказалось — **невозможно** на этом железе:
- Сейф (отдельный шифр-APFS-том, разблокировка вручную по SSH после загрузки) защищает только **холодные** данные — те, что открываешь по требованию.
- **Живые данные (iCloud Drive/Obsidian, ОС, ключи Tailscale/SSH) защитить нельзя:** iCloud жёстко держит их в `~/Library/Mobile Documents` на открытом диске (путь не сменить, в отличие от Photos), и они должны быть постоянно доступны для синхронизации. «Всегда доступно» + «зашифровано секретом из головы» + «само грузится» — взаимоисключающи (та же невозможность, что заставила снять FileVault).
- Поэтому сейф не покрывал цель → оператор его разобрал, данные вернулись на открытый диск.

**Развилка, которую НЕ обойти на Intel T2:** либо (1) сам поднимается после блэкаута (FileVault off, данные открыты), либо (2) данные зашифрованы (full-disk FileVault, но pre-boot стена → сам не встаёт). Выбрали (1).

**Мечта (шифр всего вкл. iCloud + авто-подъём + удалённая разблокировка) реальна только на Apple Silicon + macOS 26 Tahoe** (remote FileVault unlock по SSH до логина). На этом мини — нет.

Ниже — детальная запись того, **что делали** (снятие FileVault + сейф + разбор), как воспроизвести и откатить. Секции про сейф оставлены как рабочий рецепт: если однажды понадобится защитить именно ХОЛОДНЫЕ данные — они применимы.

---

## Проблема, которую чинили

Мини стоит без клавиатуры и монитора, питание в квартире нестабильное. Пока был включён **FileVault**, любой блэкаут приводил к тому, что после возврата питания мак загружался, но упирался в **pre-boot экран ввода пароля FileVault** — который появляется ДО поднятия сети. Ввести пароль headless-машине некому → мак не доходил до ОС/сети/Tailscale и «пропадал», пока его физически не подключат к телевизору с клавиатурой.

Требование оператора: мини должен **сам** восстанавливаться в сеть после потери питания и быть доступен по Tailscale, **без нового железа** (UPS/IP-KVM/доп. сервер в LAN отвергнуты), при этом **данные должны оставаться нечитаемыми при краже устройства**.

## Почему единственное решение — снять FileVault (вывод глубокого исследования)

Проверено по 14 источникам (см. deep-research 2026-07-12):

- **Remote FileVault unlock по SSH** есть только в macOS 26 Tahoe и только на Apple Silicon → на Intel T2 недоступно.
- **`fdesetup authrestart`** — одноразовый, НЕ переживает потерю питания.
- **Аналога Linux NBDE** (Clevis/Tang, сетевая авто-выдача ключа) на macOS нет.
- Значит на этом железе **нельзя одновременно** иметь и авто-загрузку, и pre-boot парольную защиту загрузочного тома.

Ключевой факт про T2: **диск шифруется железом всегда**, FileVault лишь добавляет замок паролем поверх. Поэтому снятие FileVault на T2 — быстрая метаоперация (не многочасовая перезапись), и данные остаются железно-зашифрованными, но ключ выдаётся автоматически при загрузке → мак грузится сам.

**Расплата (принята осознанно):** при снятом FileVault, если украдут машину целиком, boot-том читаем (автологин пускает в сессию; Target Disk Mode сливает диск; T2-шифрование спасает только от «выпаяли чип SSD»). Firmware password **отвергнут** — Apple его сбрасывает по подтверждению владения, данные он не шифрует и от автологина не спасает.

## Целевая архитектура

Разделение данных на две кучи:

| | Где | Защита при краже | Доступность после блэкаута |
|---|---|---|---|
| ОС + то, что нужно для авто-старта (ключи Tailscale/SSH, автологин) | boot-том, **FileVault OFF** | нет (идентичность узла отзывается удалённо) | сам |
| Реальные данные (архив, документы, проекты, медиа) | **отдельный шифр-APFS-том «Vault»**, пароль только в голове оператора | полная, крипто; Apple не поможет | только после ручной разблокировки по SSH |

## Что делалось по шагам (с командами и граблями)

Порядок важен: сначала спасти данные, потом освободить место, потом шифрование. Деструктив — только после верификации.

### 0. Диагностика (read-only)
`fdesetup status`, `pmset -g`, `diskutil apfs list`, `log show` — подтвердили: FileVault On, железо здорово (SMART Verified, 0 паник), питание настроено верно (`autorestart=1`, `womp=1`, `sleep=0`).

### 1. Снять вторую копию уникального архива ПРОЧЬ с мини
На диске лежала единственная копия аварийно спасённого архива Dropbox (24G, 122 933 файла). Пока её нет в другом месте — **никакого деструктива**.
- `rsync -a --partial mini:Dropbox-Mirror/ ~/Dropbox-Mirror-from-mini/` на ноут.
- **Грабли:** копия шла через Tailscale (~5–13 MB/s), линк рвался (torrent+Plex забивали канал; SSH «Connection reset»). Решение — авто-retry обёртка: `until rsync -a --partial -e "ssh -o ServerAliveInterval=15 -o ServerAliveCountMax=4"; do sleep 10; done`. `--partial` даёт возобновление. Apple `openrsync` (protocol 29) НЕ знает `--append-verify`/`--info` — только `--partial`.
- Сверка: `find | wc -l` источник == назначение (лишний `.DS_Store` на приёмнике — не в счёт).

### 2. Освободить место на мини (был 94% занят)
Главный объём — **Photos Library 282G**, всё синхронизировано в iCloud. (Yandex.Disk на мини всего 12M — не путать с ноутом.)
- Оператор **в приложении Photos** подтвердил статус «Синхронизировано» (из CLI это достоверно НЕ проверить — только через GUI/Screen Sharing).
- Удаление локальной библиотеки НЕ трогает iCloud: `rm -rf ~/Pictures/Photos\ Library.photoslibrary`.
- **Грабли:** foreground `rm` в интерактивном tmux **завис** (0 CPU, 0 файлов удалено — блокировка на выводе в терминал). Лечение: `kill -9` зависший + запускать в фоне без терминала: `nohup rm -rf "…" > /tmp/rmphotos.log 2>&1 & disown`. Локальный снапшот `live_…` место НЕ задержал. Освободилось 26G → 306G.

### 3. Создать шифр-сейф (оператор вводит пароль сам)
```
sudo diskutil apfs addVolume disk1 APFS Vault -passprompt
```
Спрашивает sudo-пароль, затем **новый пароль сейфа дважды**. `-passprompt` = пароль вводится интерактивно, в логи/историю/контекст ассистента не попадает. Создался `disk1s7`, смонтирован в `/Volumes/Vault`, один крипто-пользователь «Disk User».

### 4. Переложить данные в сейф и сверить
`rsync -a ~/<папка>/ /Volumes/Vault/home/<папка>/` для Documents, Desktop, Downloads, Movies, code, projects, claude-mini-demo; архив — в `/Volumes/Vault/Dropbox-Mirror`. После каждой — сверка `find | wc -l` источник == сейф, только потом удаление исходника.
- **Грабли:** `~/Documents`, `~/Desktop`, `~/Downloads` защищены TCC — по SSH `rm` даёт «Permission denied». Удалять их только через **Finder** (Screen Sharing) или с Full Disk Access. Остальное удалилось по SSH.

### 5. Снять FileVault
```
sudo fdesetup disable
```
Спрашивает sudo + имя/пароль FileVault-пользователя. На T2 — мгновенно (`fdesetup status` → Off, `diskutil` без прогресса конверсии).

### 6. Проверка перед перезагрузкой
- `fdesetup status` = Off; расшифровка не идёт.
- Сейф остаётся зашифрован; **keychain чист** → сам не откроется.
- `autoLoginUser` = venil; `pmset` autorestart=1/womp=1.
- Tailscale — системный демон (`/Library/LaunchDaemons/com.tailscale.tailscaled.plist`), sshd — системный → поднимутся ДО логина.

### 7. Headless-тест (без периферии)
Отключить монитор/клаву → `sudo reboot`. Результат: мини **сам вернулся в сеть по Tailscale за ~18 сек**, FileVault Off, автологин отработал, **сейф остался закрыт**.
- **Грабли (ложная тревога):** после первого ребута сейф был смонтирован — оказалось, оператор разблокировал его **вручную** для проверки, а не авто-ключ. Проверка отсутствия авто-ключа: `diskutil apfs lockVolume disk1s7` затем `diskutil mount disk1s7` → «encrypted and locked, use unlockVolume» = ключа нет, всё правильно.

## Как этим пользоваться дальше

В `~/.zshrc` заведены функции-обёртки (используют `VAULT_UUID`, стабильнее чем `disk1s7`):

- **`vault-open`** — открыть сейф; спросит пароль (ввод скрыт), смонтирует в `/Volumes/Vault`.
- **`vault-close`** — запереть.
- **`vault-status`** — открыт/закрыт.

Под капотом: `diskutil apfs unlockVolume <UUID> -stdinpassphrase` / `lockVolume` / `info`. Вручную то же: `diskutil apfs unlockVolume disk1s7`.

**Раскладка сейфа** (`/Volumes/Vault`): `Dropbox-Mirror/` (архив); `home/{Documents,Desktop,Downloads,Movies,code,projects,claude-mini-demo}`; `home/sops/age/keys.txt` (SOPS age-ключ — перенесён с открытого диска, `SOPS_AGE_KEY_FILE` в `.zshrc` указывает сюда → SOPS работает только при открытом сейфе). В `~` заведены симлинки `code/projects/claude-mini-demo/Dropbox-Mirror` → в сейф: старые пути работают при открытом сейфе, «висят» при закрытом (безвредно).

После блэкаута мини поднимается сам, но данные в сейфе (включая `~/code` с проектом и SOPS-ключ) закрыты, пока оператор не выполнит `vault-open` — это осознанный компромисс.

## Threat model / что защищено, что нет

- ✅ Кража машины целиком → данные в сейфе крипто-нечитаемы без пароля из головы оператора; Apple не сбросит.
- ✅ Блэкаут → мини сам в сети по Tailscale.
- ⚠️ boot-том (ОС, `~/.ssh`, состояние Tailscale, keychain, AppGate) при краже читаем → **при краже немедленно отозвать узел в Tailscale и ротировать ключи**. Настоящих секретов на boot-томе держать нельзя.
- 🔴 **Пароль сейфа невосстановим.** Забыл — данные потеряны. Хранить надёжно (голова + менеджер паролей).

## Откат (вернуть FileVault)

`sudo fdesetup enable` (снова включит pre-boot стену — мини перестанет подниматься сам после блэкаута). Сейф-том при этом не нужен и может быть удалён: `diskutil apfs deleteVolume disk1s7` (**сначала вынести из него данные!**).
