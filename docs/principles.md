# Принципы

Этот документ — контракт. Каждое решение сверяется с ним; каждое нарушение должно быть осознанным и зафиксированным в ADR.

## 1. Размытость — нарушение

В этом проекте нет фразы "оба варианта хороши". Нет "зависит от обстоятельств" без явного указания, **от чего именно зависит и где проходит граница разветвления**. Нет "может быть, стоит рассмотреть". Нет "в зависимости от предпочтений команды". Нет "это вопрос вкуса".

Если в документе появилась размытая формулировка — это не аккуратность, это уклонение от ответственности за решение. Каждая такая фраза переписывается до конкретики или удаляется.

Допустимы три формы ответа: (а) правильный вариант с обоснованием; (б) правильный вариант с явным указанием условий применимости и условий неприменимости; (в) "не знаю, требуются эмпирические данные" с описанием эксперимента, который позволит узнать. Всё остальное — отказ от позиции, маскирующийся под нейтралитет.

Особо: фраза "this is a trade-off" сама по себе не аргумент. Trade-off — это выбор. Назови, что выбрано, и скажи почему. Описание выбора без выбора — мусор.

## 2. Claude — критик. Решения принимает оператор

Claude не выбирает архитектуру. Не определяет домен. Не закрывает trade-off. Не решает, нужен ли ADR. Не решает, нужен ли тест. Не решает, что считать done. Все эти решения — оператора. Claude задаёт вопросы, требует артефакты, ловит дыры, блокирует "ну пока сойдёт". Всё.

Все агенты-критики — read-only. `adr-reviewer` не предлагает альтернатив, которые автор не рассмотрел. `domain-reviewer` не добавляет термины. `backlog-groomer` не мутирует issues. `security-reviewer` и `reliability-reviewer` не пишут код. Если агент пытается решать вместо оператора — нарушение, агент переписывается.

LLM по умолчанию выдаёт ленивые решения: дублирование вместо абстракции, обработку симптома вместо корня, костыль с TODO вместо реализации, узкий частный случай вместо обобщения, копипасту из соседнего хунка с минимальной модификацией. Это базовое поведение, не отклонение. Роль душного напарника существует, чтобы каждое такое решение ловить и блокировать. Когда модель выдаёт зелёный CI и зелёный review — проверь её ещё раз. Зелёные gate'ы не доказывают качество, они доказывают только, что эти конкретные gate'ы прошли.

## 3. Сначала детерминированный тулинг. Потом, может быть, агент

Задача механически детектируется — линтер, статический анализатор, mutation tester, property-based, AST-walker, regex. Никаких LLM. Дублирование, цикломатическая сложность, мёртвый код, TODO без issue-ref, типы, форматирование, схема API, fuzz-тестирование — всё это решается без единого токена.

LLM используется на семантику и intent: ленивое решение в коде, расхождение реализации с планом, нарушение принципа в новой строке, отсутствие явного обоснования эксплуатационных требований. Туда, куда AST не дотянется.

LLM на задаче, которую решает линтер — двойная работа, потеря времени, потеря денег, потеря трекинга. Если кто-то предложил поднять агента ради проверки, которую делает `eslint --max-complexity=10` — отказ.

Approval-режим: lint, format, typecheck, чтение, поиск, тесты, черновики — без approval. Архитектурные решения, выбор зависимостей, изменение модели данных, миграции, production config, merge в main — с approval. Граница не "что страшнее", а "что неотменимо за минуту". Откатываемое за минуту — без approval. Неотменимое — с approval.

## 4. Знание живёт в репо. В репо или нигде

Решения — `docs/decisions/`. Бэклог — issues и projects. Домен — `docs/domain/`. Принципы — `docs/principles.md`. Процедуры — `docs/runbooks/`. Уроки и анти-паттерны — `docs/anti-patterns.md`.

Голова оператора — не источник истины. Память LLM — не источник истины. Чат-сессия — не источник истины. Verbal onboarding нового человека через разговор — регресс документации, не альтернатива ей. Если знание передаётся устно — оно не в инструментах, и оно потеряется.

Lazy-detection — частный случай. Каждый раз, когда оператор ловит ленивое решение и пинает модель — паттерн идёт в `docs/anti-patterns.md`. Один pattern — одна запись. Реактивный пинок без накопления — нарушение, потому что в следующей сессии модель повторит то же самое, и время будет потрачено заново.

Тест Принципа: новый член команды или ты сам через шесть месяцев открывает репо. Час времени. Без чата, без устного объяснения, без вопросов автору. Должен понять: (а) как устроен цикл — какие команды, какие агенты, какие gate'ы; (б) что такое "архитектурно-значимо" в этом проекте; (в) типовые ловушки — на что модель ленится, какие классы ошибок здесь известны и как их избегают. Не уложился в час — недокументировано. Невозможно без разговора — регресс.

## 5. Scope — границы установки. Шаг за неё — нарушение

Claude-mini действует только в репозиториях, файлах и конфигах, куда его installer физически положил артефакты. Никаких глобальных git-конфигов, никаких path-allowlist'ов, никаких cross-project индексов, никаких системных интеграций по совпадению пути или имени. Граница инструмента — факт установки, а не паттерн.

Хук копируется напрямую в `.git/hooks/commit-msg`, `core.hooksPath` не трогается. Новый проект — явный `--install` и явный `--hook-this-repo`. Системные механизмы (global launchd, shell-rc conditions, cross-project indexing) выходят за scope — внедрение требует пересмотра принципа отдельным ADR.

---

## 6. Команды живут per-project. Глобального namespace нет

Slash-команды pipeline устанавливаются в `.claude/commands/` каждого проекта. Глобальный `~/.claude/commands/` не содержит project-bound команд. Изменение одной команды не должно ломать другие проекты.

`universal-setup.sh --target <repo>` копирует команды в проект и записывает `pipeline-version`. `--install` команды не трогает. Каждый проект обновляется явно.

## 7. Открытый формат — источник истины. Vendor — расходник

Каждый артефакт репозитория — текст в открытом формате: markdown, YAML, JSON, plain text. Любой парсер, любой текст-редактор, любой git-клиент. Артефакт, существующий только внутри проприетарной системы — например, поле в Linear, которого нет в экспорте, ID объекта в Notion, рендер в Confluence — это не артефакт проекта, а кэш сервиса. Источник истины — в репо, а не в SaaS.

Vendor-инструменты используются как удобство и кэш. GitHub Issues — да, потому что они зеркалятся в файлах и парсятся через `gh` API. Projects v2 board — кэш, статусы тикетов дублируются в коммитах и issue body. Cursor rules — нет, если они не дублируются в открытом формате (CLAUDE.md / AGENTS.md), потому что vendor умрёт, и правила умрут с ним.

Миграция между tooling одного класса — forge, runtime, IDE, MCP-клиент — выполняется без потери данных и без переписывания pipeline'а. `gh`-команды абстрагируются через единый wrapper. Field-IDs Projects v2 не зашиваются в скрипты как магические числа. Claude Code-специфичные конструкции (slash-commands, sub-agent frontmatter) хранятся в форматах с известным mapping на альтернативы (Codex CLI, Goose, любой будущий runtime).

Тест Принципа: машина без Claude Code, без `gh`, без проприетарных GUI. Только git, текст-редактор, bash. Открой репо. Прочитай. Восстанови контекст. Внеси правку. Закоммить. Что не работает в этой конфигурации — нарушение Принципа. Это не teoretический тест — это режим работы при отказе любого vendor'а.

## 8. Антихрупкость по домену. Запас 2-3×. Не 1000×

Каждое решение — функциональная корректность плюс эксплуатационная зрелость. Семь измерений — reliability, observability, recoverability, security, maintainability, operability, auditability. Каждое решение проходит явный gate по этим измерениям, релевантным для его доменной значимости. Решение без артикуляции эксплуатационных требований — не Done, даже если тесты зелёные и review APPROVE.

Глубина проверки — пропорционально домену. Платежи в банке, governance hook, миграция данных — полный набор. Логирование внутреннего скрипта — подмножество. Что считается достаточным — определяется доменом и записывается явно, не остаётся на интуицию. "Видимо, тут не так критично" — нарушение Принципа 1.

Запас прочности — два-три раза от ожидаемой нагрузки и доменных требований. Не больше. Овeринжинеринг — failure mode, такой же, как техдолг. Готовиться к нагрузке, которая никогда не придёт — потеря времени, потеря читаемости, потеря денег. Build for what is needed plus reasonable margin. Build for what might possibly happen in some hypothetical future — отказ.

Если для определения адекватного уровня нет ясности — это сигнал недостающего доменного описания, а не повод выбирать по вкусу. Возвращаемся в `docs/domain/`, фиксируем требование, потом возвращаемся к решению.

## 9. Перехват — контракт

В любой момент LLM-недоступности — отключение Claude, отключение Codex, отключение интернета, политическое блокирование региона, выкатка vendor-feature, ломающая текущую работу — оператор открывает репо и продолжает работу руками с точки остановки. Без переустановки контекста, без расспросов, без перечитывания чата.

Никакого state в context window, не материализованного на диске. Каждый шаг pipeline оставляет artifact, достаточный для продолжения без LLM. Plan недописан — текстуально читаем, помечен как недописанный с указанием, до какого пункта дошли. Имплементация на середине — branch и план состыкованы, недоделанные места явно помечены TODO с issue-ref. Никакого молчаливого skip'а. Никакого "знаю, что делать дальше, потом запишу".

Hand-off включает три уровня одновременно. Первый — код, тесты, plan.md, читаемые сами по себе. Второй — STATE.md или эквивалент: где я, что делал в последний раз, что дальше, какой следующий шаг, почему именно он. Читается за пять минут. Третий — session log как audit trail: все advisor calls, tool calls, принятые решения, отвергнутые альтернативы, обоснования. Не "что было сказано модели", а "что pipeline сделал и почему". Журнал решений, не транскрипт чата.

Человеческие тикеты, выполненные вне pipeline — без advisor, без ADR-интервью, без two-voice review, без нормального governance — не равнозначны конвейерным. Они отстают по уровню проекта. После восстановления LLM такие тикеты проходят supervisory re-pass — pipeline в audit-режиме читает реализацию, восстанавливает недостающие артефакты задним числом (plan, ADR если требовался, domain-update если требовался), прогоняет через критиков, two-voice review на готовом коммите. Что найдено — фиксится отдельным тикетом или подтверждается как осознанный compromise. Цель — не наказать оператора за работу без pipeline'а, а дотянуть результат до общего уровня репо.

Continuity не блокирующий приоритет в моменте — LLM пока работают, перехват редкий случай. Но контракт зафиксирован, и pipeline строится так, чтобы при отказе оператор не остался с непонятным состоянием на руках.

## Definition of Done

Изменение **Done** когда все условия истинны:

- [ ] ADR открыт и смерджен, если изменение архитектурно-значимо
- [ ] Domain-доки обновлены, если изменилась граница BC или термин
- [ ] Unit-тесты написаны; integration-тесты для cross-BC путей; coverage ≥ project floor (дефолт 80%)
- [ ] `/review` (Claude) одобрил
- [ ] `adversarial-critic` запущен внутри `/review` (сканирует 8 классов LLM-ленивых паттернов, см. `docs/runbooks/feature-pipeline.md §6`); BLOCK-findings устранены ИЛИ задокументированы как осознанный компромисс в PR-треде
- [ ] `/codex-review` (Codex) одобрил ИЛИ создан `type:deferred-review` issue с обоснованием graceful degradation
- [ ] Разногласия между Claude и Codex разрешены в PR-треде (консенсус или фиксация disagreement)
- [ ] Human self-review выполнен
- [ ] Security scans clean: `uv pip audit` / `cargo audit` / `npm audit --audit-level=high` / `govulncheck` — в зависимости от языка
- [ ] Docs обновлены: README (при публичных изменениях), relevant runbook, CHANGELOG (через release-please)
- [ ] Human-facing docs reviewed: если PR меняет `docs/runbooks/`, `docs/architecture/`, `docs/principles.md`, `README.md` — `docs-reviewer` одобрил ИЛИ изменений в этих путях нет
- [ ] Reliability reviewed: если PR прод-bound (`bootstrap/`, `.github/workflows/`, `.git/hooks/`, label `prod-bound`) — `reliability-reviewer` одобрил ИЛИ изменений в прод-bound путях нет
- [ ] CI зелёный на всех required jobs
- [ ] Conventional Commits; governance-hook проверку прошёл
- [ ] PR body ссылается на issue (`Closes #NNN`) и на ADR (`Implements docs/decisions/NNNN-*.md`) если был

Этот чек-лист копируется в `pull_request_template.md` и проверяется на каждом PR.

## Что значит «архитектурно-значимо» (триггер для ADR)

Решение требует ADR, если истинно **хотя бы одно**:

- Добавляется или удаляется зависимость, которая становится cross-cutting (логгер, ORM, HTTP-клиент)
- Меняется граница bounded context или сигнатура межконтекстного контракта
- Выбирается хранилище, очередь, или иной инфраструктурный компонент
- Устанавливается или отменяется публичный API
- Принимается ограничение, которое будет трудно снять через 6 месяцев (например, единственный язык, единственная БД, единственная облачная платформа)
- Меняется модель безопасности или модель данных

Если ни одно — это story, а не decision. `/plan` достаточно.

## Что значит «нетривиальная задача» (триггер для advisor × 2)

Задача требует два вызова advisor, если истинно **хотя бы одно**:

- Затрагивает более одного модуля/пакета
- Имеет неочевидные edge cases
- Конкурирует с существующим похожим кодом (дублирование не очевидно)
- Содержит асинхронность, concurrency, rare-path обработку ошибок

Тривиальное (advisor не нужен): форматирование, rename, линт-фиксы, однострочные bug-fixes с тестом, обновление строки в docs.

## Operational rules (НЕ принципы)

Внедряются через скиллы, runbook'и и чек-листы:

- **Детерминированный тулинг приоритетнее LLM-проверок** — формулируется в /review skill, в выборе верификаторов. Это не принцип, это применение Принципа 3.
- **Gate ROI обязателен** — каждый gate производит audit trail (frequency, blocked-real-issue count, bypass count, false-positive count, cost). Weekly /gate-audit. Gate без доказанной пользы — удаляется. Pipeline — стамеска, не бюрократия.
