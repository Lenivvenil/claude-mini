# 0031. Deliver the harness as a project-scoped Claude Code plugin with a two-layer assess/apply deployment

* Status: proposed
* Superseded-by: ~
* Date: 2026-09-26
* Deciders: Lenivvenil (operator); draft by Claude
* Tags: architecture, installation, security, configuration

## Context and Problem Statement

Установщик v1 действует за границей проекта. Он дописывает переменные моделей в `~/.zshrc` (`bootstrap/universal-setup.sh:758–779`), патчит хуки в `~/.claude/settings.json` (`:487` и далее), кладёт симлинки в `~/bin` (`:813`), копирует агентов и скиллы в `~/.claude/` (`:409–432`). Stop-хук пишет `STATE.md` и `session-log/` в текущий каталог любой сессии (`bootstrap/hooks/stop-hook.sh:91,105`). Это нарушает `docs/principles.md §5`, и конвейер разработки попадает в сессии, где владелец делает анализ, а не разработку. Владелец поставил требования 2026-09-26: сохранить идеи v1, сделать харнесс локальным для проектов разработки, развёртывать его двумя частями (машина, затем харнесс), и голый Claude по просьбе «разверни мой харнесс для этого проекта» должен справиться сам, не задев соседние проекты.

## Decision Drivers

* Граница по построению. Сессия в проекте, где харнесс не включён, не видит ни одного его агента, скилла или хука. Проверяется наблюдением, а не только хешами.
* Самостоятельное развёртывание. Агент без контекста находит точку входа в репозитории и доводит развёртывание до проверенного результата.
* Минимальная дельта. Сначала оценка готовности хоста по чеклисту, затем применяется только недостающее и только в указанном проекте.
* Обратимость развёртывания. Каждое изменение записано в манифест, откат возвращает исходные байты, частично применённый файл невозможен.
* Без хардкода. Версии, ветки, правила коммитов, критики, пороги и идентификаторы досок читаются из конфига с валидацией.
* Сохранение v1. Каждый компонент v1 переносится с проверкой, что его возможность работает на новом месте. Удаление только по описи.

## Considered Options

* **Option A.** Плагин Claude Code, включаемый только на уровне проекта (`--scope local` или `project`), плюс команда `setup/harness` с двумя слоями и конфиг проекта.
* **Option B.** Оставить `universal-setup.sh`, но раскладывать все артефакты в каталог проекта через `--target` для агентов, скиллов и хуков.
* **Option C.** Плагин на уровне user с защитой во время выполнения. Хуки и скиллы сами проверяют маркер проекта и молчат вне его (подход #303/#305).

## Decision Outcome

Chosen option: **Option A**, because только он даёт границу по построению (драйвер 1) штатным механизмом Claude Code, а не дисциплиной. Опция B копирует артефакты в каждый проект, и копии расходятся с источником. ADR-0018 для команд вводил файл `pipeline-version` в проекте и константу в `feature.md`, но и сам признавал, что продвижение источника этим не ловится. Опция B распространила бы эту проблему на агентов, скиллы и хуки и оставила бы установщик вторым источником истины. Опция C держит границу на проверке внутри каждого компонента, и новый компонент без проверки снова течёт наружу. Решение опирается на `docs/principles.md §5` (граница — факт установки) и §9 (каждый шаг оставляет артефакт на диске). §8 определяет глубину проверок, п. 8 контракта.

Контракт:

1. **Доставка.** Ядро живёт в `plugin/`, каталог-маркетплейс в `.claude-plugin/marketplace.json`. Включение только `--scope local` или `--scope project`. Инструменты и документация не предлагают установку без явной области.
2. **Два слоя развёртывания.** `setup/harness assess | apply | verify | uninstall --project DIR [--layer machine|project]`.
   * `assess` только читает. Печатает чеклист со статусами `ready | missing | wrong-version | not-applicable | needs-manual` и минимальную дельту.
   * `apply` выполняет только дельту. Каждый пункт атомарен: запись о намерении, проверка кандидата синтаксисом и поведением, копия оригинала, подмена, запись о завершении. Сбой возвращает пункт в исходное состояние.
   * Установка отсутствующей системной программы выполняется только для пунктов, явно названных в `--allow-system`.
   * Шаги с графическим интерфейсом и секретами остаются ручными (`needs-manual`). Это сохраняет довод ADR-0008.
   * После каждой команды печатается отчёт «Сломано / Не сделано / Работает», каждый пункт перепроверен в момент отчёта.
3. **Разрешённый след развёртывания вне проекта.** Перечень закрытый:
   * записи и кеш самого Claude Code в `~/.claude/plugins/`, сверяются по отдельным записям;
   * собственные каталоги CodeBurn `~/.cache/codeburn` и `~/.config/codeburn`, если CodeBurn включён;
   * системные программы, названные в `--allow-system`.

   Любая другая запись развёртывания вне проекта — нарушение, тест падает. Рабочее состояние самих сессий Claude Code (транскрипты, снимки оболочки и подобное) записью развёртывания не считается. Тест держит его в изолированном каталоге конфигурации или перечисляет эти пути явно и исключает их из сравнения.
4. **Конфиг.** Значения по умолчанию в `plugin/config/defaults.json`, переопределение в `<project>/.claude/claude-mini.json`. Валидация отвергает неизвестные ключи.
5. **Внешние сервисы необязательны.** Без Codex, Jev, CodeBurn или сети харнесс работает в урезанном режиме с явным сообщением и не ломает проект.
6. **Jev только советует.** Он не решает о коммите, merge, закрытии задач, разрушительных действиях и отмене обязательных проверок.
7. **Непрерывность.** Автоматический Stop-хук заменяется явным скиллом передачи работы, который пишет только внутри проекта. Скиллы стадий (`feature`, `implement`) вызывают его в конце стадии. Порядок «сначала журнал, потом снимок» и предупреждение о незаполненных полях снимка (ADR-0024, подрешение 9) переходят в этот скилл.
8. **Глубина проверок соразмерна (§8).** Полный набор (атомарность, откат, приёмка голым Claude) — для хука коммитов и для `setup/harness`. Для вспомогательных скриптов скиллов — подмножество: синтаксис, свои тесты, запрет записи вне проекта.
9. **Git-хук в проекте (ADR-0011)** становится необязательным пунктом слоя проекта. По умолчанию он выключен. Коммиты из Claude проверяет хук плагина. Хук в `.git/hooks` остаётся способом проверять коммиты человека и ставится только в указанный проект.

### Positive Consequences

* Аналитические сессии и чужие проекты не видят харнесса. Это проверяется тестом, а не обещанием.
* Развёртывание повторяемо и обратимо. Повторный `apply` ничего не меняет, `uninstall` возвращает исходные хеши.
* Идеи v1 сохраняются вместе с историей git.

### Negative Consequences

* Нулевого следа вне проекта нет. Реестр и кеш плагинов Claude Code лежат в `~/.claude/plugins/`, это штатное поведение, и его приходится сверять по записям.
* Харнесс становится зависим от механизма плагинов Claude Code. По §7 это расходник вендора. Агенты и скиллы остаются markdown с frontmatter и читаются без Claude Code, но их доставка и включение завязаны на этот механизм.
* Передача работы теперь зависит от вызова скилла. Если стадия оборвалась до конца, снимка нет. Автоматический Stop-хук писал его всегда, и это ослабляет §9.
* Пока на машине стоит v1, `universal-setup.sh:409–432` копирует агентов и скилл из `plugin/` в `~/.claude/`. На время сосуществования граница по построению на такой машине не выполняется.
* Появляется новый код: `setup/harness`, манифест, валидатор конфига, приёмочный тест. Его надо сопровождать.
* Приёмочный тест с голым Claude стоит лимитов подписки и идёт только локально. В CI без ключа API он не запускается.
* Перенос долгий, около десяти фаз. Пока он идёт, v1 и v2 живут рядом, а проект `~/Projects/likec4` уже включает плагин из этого репозитория на уровне local.

## Pros and Cons of the Options

### Option A

* Good, because граница обеспечена штатным механизмом включения плагина.
* Good, because один источник истины (`plugin/`), версия в `plugin.json`.
* Bad, because штатный реестр плагинов всё равно пишет в `~/.claude/plugins/`.
* Bad, because нужен собственный слой `setup/harness` для машины и заготовки проекта.
* Bad, because доставка завязана на механизм плагинов одного вендора.

### Option B

* Good, because не зависит от механизма плагинов Claude Code.
* Bad, because копии в каждом проекте расходятся с источником, и ADR-0018 этого не решил даже для команд.
* Bad, because установщик остаётся вторым источником истины и снова обрастает глобальными шагами.

### Option C

* Good, because одна установка на машину.
* Bad, because граница держится на проверке внутри каждого компонента. Пропуск проверки в новом компоненте — утечка во все сессии.
* Bad, because хуки на уровне user выполняются в каждой сессии, в том числе аналитической.

## Confirmation

* `tests/plugin-scope/no-plugin-no-writes.sh`. Сессия `claude -p` в проекте, где плагин не включён. Проверяется, что `claude-mini` нет в списке загруженных плагинов, его скиллов и агентов нет, а плохой коммит не отклоняется, потому что хук не срабатывает. Хеши дерева проекта до и после совпадают. Тест идёт в изолированном `$HOME`: на машине с установленным v1 глобальный хук ADR-0004 отклонит коммит, и тест честно упадёт.
* `tests/acceptance/deploy-bare.sh`. Голый `claude -p` получает фразу «deploy my harness for this project». Проверяется, что плагин загружен, хук отклоняет плохой коммит и пропускает хороший, соседний проект не видит плагина. Весь `$HOME` сверяется с закрытым перечнем п. 3 контракта, а после `uninstall` всё возвращается к исходному. Прогон на реальной машине после фазы развёртывания и после удаления v1.
* Тесты `setup/harness`: пустая дельта на готовом хосте, повторный `apply` без изменений, отказ системной установки без согласия, сбой посреди пункта без изменения цели, откат до исходных хешей.
* Валидатор конфига отвергает файл с неизвестным ключом.
* Урезанный режим: без `codex`, без ключа Jev и без сети `apply` завершается успешно, а отчёт называет урезанные возможности.
* Jev только советует: при любом ответе Jev обязательные проверки выполняются. Тест подменяет ответ Jev и проверяет, что шлюз не пропущен.
* После удаления v1 поиск `universal-setup` по поверхностям развёртывания (README, DEPLOY.md, `plugin/`, `setup/`) пуст.

## Reversibility

Развёртывание обратимо командой `uninstall`. Само решение обратимо через историю git: перед удалением v1 последний коммит с `bootstrap/` помечается в описании PR удаления. Возврат к v1 — `git revert` этого PR и повторная установка v1. Цена возврата — возвращается глобальный след v1, ради устранения которого принято это решение.

## Re-visit Trigger

* Claude Code даёт хранить реестр плагинов внутри проекта. Тогда пересмотреть п. 3 контракта.
* Приёмочный тест с голым Claude дважды подряд падает на поддерживаемом хосте по причине вне харнесса.
* Нужен второй тип хоста (Linux). Тогда проверить, что чеклист машины покрывает его без форка `setup/`.
* Передача работы через явный скилл теряет снимок в реальной работе дважды за месяц. Тогда вернуть автоматический триггер в пределах проекта.
