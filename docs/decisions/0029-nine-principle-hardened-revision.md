# 0029. Adopt nine-principle hardened revision of docs/principles.md

* Status: accepted
* Superseded-by: ~
* Date: 2026-05-07
* Deciders: Venil (operator)
* Tags: governance, principles, pipeline

## Context and Problem Statement

На 2026-04-29 проведено интервью с research-Claude о состоянии пайплайна. Интервью вскрыло три структурных разрыва: (1) существующие четыре принципа не называли lazy-by-default поведение LLM явной угрозой — gate'ы зеленели, качество проседало без фиксации; (2) не было ни одного принципа, блокирующего vendor lock-in или обязывающего продолжать работу без LLM; (3) граница «строить на 2-3×, не на 1000×» нигде не зафиксирована, что открывало путь к overengineering под видом «надёжности». Триггер не в хронологии — в том, что три класса нарушений уже происходили без инструмента их именования.

## Decision Drivers

* Lazy-detection должна быть первоклассной инженерной задачей, а не надеждой на внимательность оператора в сессии — без принципа нет и механизма фиксации в `docs/anti-patterns.md`
* Пайплайн должен быть воспроизводим без Claude Code, без GitHub, без интернета — continuity-контракт нужен как принцип, иначе он остаётся благим пожеланием
* Vendor-инструмент (Claude Code, GitHub, Cursor) — расходник; все артефакты должны читаться plain text + git + bash — без принципа это тест без grade
* Overengineering — такой же failure mode, как техдолг; граница «2-3×» должна быть named constraint, не интуицией
* Существующие P1–P4 были сформулированы мягко («красные флаги», «душный напарник») — размытость нарушала Принцип 1 в самих принципах

## Considered Options

* **Вариант A.** Оставить четыре принципа, дополнить runbook'и и operational rules отдельными нормами
* **Вариант B.** Принять девятипринципную редакцию in-place: ужесточить P1–P4, оставить P5–P6, добавить P7–P9 — выбран
* **Вариант C.** Разделить на два документа: immutable core principles + mutable operational norms (2-tier)

## Decision Outcome

Chosen option: **Вариант B**, потому что он устраняет все пять drivers в одном контракте и не создаёт новой поверхности рассинхронизации. Принципы 1–4 ужесточены до категорических запретов вместо ориентиров — это применение самого P1 («размытость — нарушение») к документу принципов. Три новых принципа (P7: открытый формат; P8: антихрупкость по домену; P9: перехват-контракт) закрывают ровно те три структурных разрыва, что выявило интервью. Оба альтернативных варианта оставляли разрывы открытыми: Вариант A размывал контракт по нескольким файлам, нарушая P4 (знание живёт в репо); Вариант C добавлял документ без необходимости — нарушение P8 (запас 2-3×, не overengineering). Решение отсылает к P4 (`docs/principles.md` — единственный источник истины для контракта проекта).

### Positive Consequences

* Lazy-detection получает именованный принцип (P2, P3) и прямую дорогу к `docs/anti-patterns.md`; каждый раз, когда оператор ловит лень — запись идёт в файл, не теряется между сессиями
* Continuity-контракт (P9) описывает точно три уровня hand-off — operator может продолжать работу без LLM с точки остановки
* Vendor independence (P7) — новый тест: «машина без Claude Code, без `gh`, только git+текст+bash» становится обязательным при выборе любого инструмента

### Negative Consequences

* Девять принципов труднее удержать в голове, чем четыре — порог входа для новичка вырос; «тест за час» P4 теперь охватывает девять пунктов
* P8 (антихрупкость по домену) требует явного указания доменного уровня перед каждым решением о глубине проверки — это дополнительный артефакт к каждому ADR и к DoD
* P9 (перехват-контракт) материализует STATE.md и session log как обязательные артефакты каждой сессии — дополнительные работы, которых не было в старом pipeline
* Definition of Done, производный от принципов, вырос с 10 до 14 пунктов — больше чекбоксов, больше поверхности для compliance gap

## Pros and Cons of the Options

### Вариант A — Оставить четыре принципа, дополнить runbook'и

* Good, because низкий порог изменения — существующий контракт не ломается
* Good, because операционные нормы можно обновлять независимо от принципов
* Bad, because lazy-detection по-прежнему не именована как принцип — нет механизма для `docs/anti-patterns.md` accumulation
* Bad, because continuity и vendor independence остаются в runbook'ах, а не в контракте — нарушение P4 (знание живёт в репо)
* Bad, because «красные флаги» и «душный напарник» — мягкие формулировки, которые сами нарушают P1

### Вариант B — Девятипринципная редакция in-place (выбран)

* Good, because единый документ-контракт без рассинхронизации между принципами и нормами
* Good, because P1–P4 ужесточены до запретов — документ соответствует сам себе
* Good, because P7–P9 закрывают три структурных разрыва одним PR
* Bad, because порог входа выше — девять принципов длиннее
* Bad, because каждый новый принцип добавляет DoD-пункты и friction к pipeline

### Вариант C — 2-tier: core principles + operational norms (отдельные файлы)

* Good, because нормы обновляются без изменения контракта
* Bad, because два файла расходятся в терминологии — нарушение P4
* Bad, because не решает проблему мягкости P1–P4 — они остаются в core без ужесточения
* Bad, because создаётся дополнительная поверхность рассинхронизации — нарушение P8 (overengineering)

## Confirmation

Раз в месяц: проверить, что каждый открытый ADR ссылается хотя бы на один принцип. Раз в квартал: прочитать `docs/principles.md` и `docs/anti-patterns.md` вместе — если в anti-patterns есть паттерн, не покрытый ни одним принципом, это сигнал к пересмотру. Порог пересмотра: три нарушения одного принципа за четыре недели без ADR-поправки означают, что принцип аспирационный, а не оперативный.

## Re-visit Trigger

Когда в проект входит второй оператор ИЛИ когда один из P7–P9 нарушается три раза подряд без ADR-фиксации — это сигнал, что принцип слишком дорог или неясен и требует переформулировки или разделения.
